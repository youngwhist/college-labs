## 1. Введение

### 1.1. Назначение документа

Документ описывает требования к веб-приложению «StudyTrack» и предназначен для заказчика (учебного заведения), разработчиков, тестировщиков и сопровождающего персонала. Документ является основой для проектирования, разработки и приёмочного тестирования системы.

### 1.2. Область применения продукта

**StudyTrack** — веб-приложение для студентов и преподавателей колледжа (СПО), в котором:
- преподаватель публикует задания и выставляет оценки;
- студент видит список заданий и сроки, сдаёт работы и получает обратную связь;
- обе стороны получают уведомления о новых заданиях, сроках и оценках.

Система **не** заменяет официальный электронный журнал и **не** занимается расписанием занятий.

### 1.3. Определения и сокращения

| Термин | Определение |
|---|---|
| FURPS+ | Модель классификации требований: Functionality, Usability, Reliability, Performance, Supportability и «+» — ограничения проектирования, реализации, интерфейсов, физические и юридические |
| SRS | Software Requirements Specification — спецификация требований к ПО |
| Функциональное требование | Описывает, **что** система должна делать |
| Нефункциональное требование | Описывает, **как** (насколько хорошо) система должна это делать |
| ПДн | Персональные данные |
| RPS | Requests per second — запросов в секунду |
| MTTR | Mean Time To Repair — среднее время восстановления после сбоя |

## 2. Общее описание

### 2.1. Пользователи системы

| Роль | Описание | Основные задачи |
|---|---|---|
| Студент | Обучающийся группы | Смотреть задания, сдавать работы, видеть оценки |
| Преподаватель | Ведёт дисциплину | Создавать задания, проверять работы, ставить оценки |
| Администратор | Сотрудник колледжа | Управлять пользователями, группами и дисциплинами |

### 2.2. Среда функционирования

- Клиент: браузеры Chrome, Firefox, Safari, Яндекс Браузер последних двух версий; компьютер и смартфон.
- Сервер: Linux, Python 3.11+, PostgreSQL 15+.
- Размещение серверов — на территории РФ.

### 2.3. Выбор элементов FURPS+ для проекта

| Категория FURPS+ | Значимость для StudyTrack | Почему |
|---|---|---|
| **F** — Functionality (функциональность) | Высокая | Основная ценность продукта — задания, сдача работ, оценки |
| **U** — Usability (удобство) | Высокая | Пользуются студенты и преподаватели без технической подготовки, часто с телефона |
| **R** — Reliability (надёжность) | Высокая | Потеря сданной работы или оценки недопустима |
| **P** — Performance (производительность) | Средняя | Пиковая нагрузка — перед сроками сдачи |
| **S** — Supportability (поддержка) | Средняя | Систему будет сопровождать ИТ-отдел колледжа |
| **+** Ограничения (проектирование, реализация, интерфейсы, юридические) | Высокая | Работа с персональными данными студентов (152-ФЗ) |

Атрибуты каждого требования (по ISO/IEC/IEEE 29148): уникальный идентификатор, формулировка, приоритет (MoSCoW: **M** — обязательно, **S** — желательно, **C** — возможно), обоснование.

## 3. Требования

### 3.1. Функциональные требования (F — Functionality)

| № | Требование | Описание | Приоритет | Обоснование |
|---|---|---|---|---|
| F-01 | Регистрация и вход | Система должна обеспечивать вход по логину (e-mail) и паролю; учётные записи создаёт администратор | M | IEEE 830-1998, п. 5.3.2 — функции системы; ГОСТ 34.602-2020 — требования к функциям |
| F-02 | Разграничение ролей | Система должна предоставлять права в зависимости от роли: студент, преподаватель, администратор | M | ISO/IEC 25010 — защищённость (конфиденциальность); принцип минимальных привилегий |
| F-03 | Создание задания | Преподаватель должен иметь возможность создать задание: название, описание, срок сдачи, максимальный балл, вложения | M | Основной сценарий использования (use case) преподавателя; IEEE 830-1998, п. 5.3.2 |
| F-04 | Список заданий | Студент должен видеть список заданий своей группы со статусом («не сдано», «на проверке», «оценено») и сроком | M | Основной сценарий использования студента |
| F-05 | Сдача работы | Студент должен иметь возможность загрузить ответ: текст в формате Markdown и файлы до 25 МБ каждый | M | Основной сценарий использования; ограничение размера — защита от перегрузки хранилища |
| F-06 | Проверка и оценка | Преподаватель должен иметь возможность поставить оценку от 2 до 5 и оставить комментарий к работе | M | Основной сценарий использования; шкала соответствует системе оценивания СПО |
| F-07 | Уведомления | Система должна уведомлять студента о новом задании, приближении срока (за 24 ч) и выставленной оценке | S | Снижает число пропущенных сроков; MoSCoW — желательная функция |
| F-08 | Журнал оценок | Система должна формировать сводную таблицу оценок группы по дисциплине с экспортом в .xlsx | S | Потребность преподавателя в отчётности |
| F-09 | Поиск и фильтр | Пользователь должен иметь возможность искать задания по названию и фильтровать по статусу и дисциплине | C | Удобство при большом числе заданий; MoSCoW — возможная функция |
| F-10 | История изменений | Система должна сохранять историю версий сданной работы и изменений оценки с указанием автора и времени | M | ISO/IEC 25010 — защищённость (неотказуемость, отслеживаемость) |

### 3.2. Требования к удобству использования (U — Usability)

| № | Требование | Описание | Приоритет | Обоснование |
|---|---|---|---|---|
| U-01 | Время освоения | Новый пользователь должен выполнить основную задачу (сдать работу / создать задание) без обучения не более чем за 5 минут | M | ISO/IEC 25010 — удобство использования (изучаемость) |
| U-02 | Число действий | Сдача работы должна выполняться не более чем за 3 перехода от главной страницы | S | ISO/IEC 25010 — работоспособность (operability) |
| U-03 | Адаптивность | Интерфейс должен корректно отображаться на экранах шириной от 360 до 1920 пикселей | M | Большинство студентов заходят со смартфона; ISO/IEC 25010 — адаптируемость |
| U-04 | Доступность | Интерфейс должен соответствовать WCAG 2.1 уровня AA: контраст текста не менее 4.5:1, управление с клавиатуры, подписи к элементам | S | WCAG 2.1; ISO/IEC 25010 — доступность |
| U-05 | Язык | Весь интерфейс и сообщения должны быть на русском языке | M | Целевая аудитория — русскоязычные колледжи |
| U-06 | Понятные ошибки | Сообщения об ошибках должны объяснять причину и способ исправления (например, «Файл больше 25 МБ — уменьшите размер») | M | ISO/IEC 25010 — защита от ошибок пользователя |

### 3.3. Требования к надёжности (R — Reliability)

| № | Требование | Описание | Приоритет | Обоснование |
|---|---|---|---|---|
| R-01 | Доступность системы | Система должна быть доступна не менее 99.5% времени в месяц (не более 3.6 ч простоя) | M | ISO/IEC 25010 — надёжность (доступность); ГОСТ 34.602-2020 — требования к надёжности |
| R-02 | Резервное копирование | База данных и файлы должны копироваться ежедневно; копии хранятся не менее 30 дней | M | ГОСТ 34.602-2020 — сохранность информации при авариях |
| R-03 | Восстановление | Время восстановления после сбоя (MTTR) — не более 4 часов; потеря данных — не более чем за последние 24 часа | M | ISO/IEC 25010 — восстанавливаемость |
| R-04 | Сохранность ответа | При обрыве связи во время сдачи работы введённый текст должен сохраняться как черновик и не теряться | S | ISO/IEC 25010 — отказоустойчивость |
| R-05 | Защита данных | Пароли должны храниться только в виде хеша (bcrypt/argon2), передача данных — только по HTTPS (TLS 1.2+) | M | ISO/IEC 25010 — защищённость; 152-ФЗ, ст. 19 — меры по защите ПДн |
| R-06 | Защита от перебора | После 5 неверных попыток входа учётная запись должна блокироваться на 15 минут | S | ISO/IEC 25010 — защищённость (подлинность) |

### 3.4. Требования к производительности (P — Performance)

| № | Требование | Описание | Приоритет | Обоснование |
|---|---|---|---|---|
| P-01 | Время отклика | 95% страниц должны открываться не дольше 2 секунд при скорости соединения от 10 Мбит/с | M | ISO/IEC 25010 — временные характеристики; исследования удобства: после 2–3 с пользователи начинают уходить |
| P-02 | Одновременные пользователи | Система должна обслуживать не менее 1000 пользователей одновременно без роста времени отклика выше P-01 | M | Оценка: колледж ~3000 студентов, пик — вечер перед сроком сдачи; ISO/IEC 25010 — ёмкость |
| P-03 | Пропускная способность | Сервер должен обрабатывать не менее 200 запросов в секунду | S | Расчёт из P-02: 1000 пользователей × 1 запрос в 5 с = 200 RPS |
| P-04 | Загрузка файлов | Файл размером 25 МБ должен загружаться не дольше 30 секунд при скорости 10 Мбит/с | S | 25 МБ × 8 = 200 Мбит ÷ 10 Мбит/с = 20 с + запас на обработку |
| P-05 | Использование ресурсов | При нагрузке P-02 загрузка процессора сервера не должна превышать 70% | C | ISO/IEC 25010 — использование ресурсов; запас для пиков |

### 3.5. Требования к поддержке (S — Supportability)

| № | Требование | Описание | Приоритет | Обоснование |
|---|---|---|---|---|
| S-01 | Стандарт кода | Исходный код должен соответствовать PEP 8 и проверяться pylint (оценка не ниже 9/10) | M | ISO/IEC 25010 — сопровождаемость (анализируемость) |
| S-02 | Покрытие тестами | Покрытие кода автоматическими тестами должно быть не ниже 80% | M | ISO/IEC 25010 — тестируемость |
| S-03 | Контроль версий | Исходный код должен храниться в Git; изменения — через ветки и проверку кода (pull request) | M | Практика конфигурационного управления; ISO/IEC 25010 — модифицируемость |

| S-05 | Журналирование | Система должна записывать в журнал ошибки и действия пользователей с хранением 90 дней | M | ISO/IEC 25010 — анализируемость; расследование инцидентов |

## 5. Проверка качества требований по IEEE 830-1998

Стандарт IEEE 830-1998 (п. 4.3) определяет 8 характеристик хорошей спецификации. Проверка документа:

| Характеристика (IEEE 830) | Как выполнена в документе |
|---|---|
| Корректность | Каждое требование отражает реальную потребность одной из ролей (раздел 2.1) |
| Однозначность | Требования сформулированы через «должна» и содержат числа: 2 с, 99.5%, 25 МБ, 1000 пользователей |
| Полнота | Охвачены все категории FURPS+ и все роли пользователей |
| Непротиворечивость | Связанные требования согласованы: P-03 рассчитано из P-02, S-07 — из R-01 |
| Ранжированность | У каждого требования есть приоритет по MoSCoW |
| Проверяемость | Каждое нефункциональное требование измеримо и может быть проверено тестом |
| Модифицируемость | Требования сгруппированы по категориям и имеют уникальные идентификаторы |
| Трассируемость | У каждого требования есть идентификатор и обоснование со ссылкой на источник |

## 6. Выводы

1. Изучена модель **FURPS+**: она делит требования на функциональные (F) и нефункциональные (U, R, P, S), а «+» добавляет ограничения проектирования, реализации, интерфейсов, физические и юридические. Для StudyTrack использованы все категории, так как продукт работает с персональными данными и важен для учебного процесса.
2. Разработано **40 требований** к веб-приложению StudyTrack, каждое с уникальным идентификатором, приоритетом и обоснованием.
3. Структура документа построена по **IEEE 830-1998** (введение, общее описание, конкретные требования), формулировки — по **ISO/IEC/IEEE 29148:2018**, нефункциональные требования — по модели качества **ISO/IEC 25010**. Учтены российские нормы: **ГОСТ 34.602-2020**, **ГОСТ 19.201-78** и **152-ФЗ**.
4. Главное отличие хорошего нефункционального требования — **измеримость**. «Система должна быть быстрой» проверить нельзя, а «95% страниц открываются не дольше 2 секунд» — можно.
5. Проверка по восьми характеристикам IEEE 830 показала, что спецификация корректна, однозначна, проверяема и трассируема, поэтому может служить основой для проектирования и приёмочного тестирования.
